How Dynamics Model-Driven Apps Handle Loading Large Tables

Dynamics model-driven apps do not load an entire large Dataverse table at once. Instead, they rely on server-side paging, grid virtualization, and filtered views to keep the user interface responsive even when tables contain millions of rows.

Key Mechanics

  • Server-side paging: Dataverse returns only a page of records per query (up to platform limits). Additional pages are retrieved only when the user scrolls or navigates, so the app never pulls the full dataset in a single request.
  • Grid virtualization: The model-driven grid renders only the rows that are visible on screen. As the user scrolls, the grid requests the next page of data. Sorting and filtering are executed on the server, minimizing client-side load.
  • View design and column minimization: Views define which columns and filters are applied. Keeping views narrow (fewer columns) and well-filtered (e.g., “My Active”, “Last 30 days”) reduces payload size and improves load time.
  • Paging cookies: Under the hood, FetchXML paging cookies are used to support consistent ordering and efficient paging across large datasets.
  • Virtual tables for huge or external data: When datasets are extremely large or live in external systems, virtual tables expose that data in the model-driven UI without storing everything in Dataverse.

What Happens When a View Opens

  1. Dataverse retrieves only the first page of records for the view.
  2. The grid renders just the visible rows using UI virtualization.
  3. Scrolling, sorting, or filtering triggers new paged queries.
  4. The app never attempts to load the entire table in one operation.

Together, these mechanisms allow Dynamics model-driven apps to handle very large tables while maintaining good performance and a smooth user experience.
